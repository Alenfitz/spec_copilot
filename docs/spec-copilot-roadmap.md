# spec-copilot Roadmap（Harness Engineering 视角）

## 一、重新定义这件事

过去我们容易把 `spec-copilot` 理解成一套“规范提示词 + gate 命令”的流程框架。

但经过多轮真实实验，尤其是 DeepSeek、MiniMax 一类模型在复杂需求下的表现，我们需要把它重新定义得更准确一些：

**`spec-copilot` 正在从“规范驱动开发流程”演进为一套 Harness Engineering System。**

它的目标不是让模型突然变得听话，也不是承诺“只要用了规范就不会跑偏”。

它真正要做的是三件事：

1. 把模型纳入一个可审计、可约束、可比较的工程系统里
2. 让违规、降级、取巧和信息断层尽早暴露，而不是事后复盘才发现
3. 让交付结果不只剩最终代码，还保留足够的过程证据，支持后续评审、复盘和模型能力比较

所以后续不应该再只问：

- 这次是不是又加了一个 gate
- 这次是不是又补了一条提示词

而应该问：

- 这次是在补 `Constraints`
- 还是在补 `Feedback Loops`
- 还是在补 `Tool Orchestration`
- 还是在补 `Structured Context`
- 还是在补 `Entropy Control`

这五个维度，才是后续版本规划的主坐标。

---

## 二、为什么要这样重构

三轮真实实验已经把问题暴露得很清楚：

- 有些模型会理解规范，但在用户催促或任务压力下直接越阶段开发
- 有些模型会写出“看起来完整”的实现，但主流程并没有真正闭环
- 有些模型在 `task.md` 自评里已经承认自己只做到了 `80/90` 分，却仍继续推进
- 有些问题不是模型不会，而是任务太大、上下文太散、后续 reviewer 读不到前面的人类决策

这说明原来的问题并不只是“提示词不够强”。

更深一层的问题是：

**我们缺的是一套围绕模型执行行为而设计的控制系统。**

也就是说，规范本身只是其中一层；真正要补的是：

- 约束层
- 反馈层
- 编排层
- 上下文层
- 熵控制层

这就是 harness engineering 的视角。

---

## 三、现实边界

先把边界说清楚，避免自欺欺人。

### 1. 规范本身不能真正阻止模型写文件

只要宿主工具还允许模型直接改源码，那么 npm 包里的 prompt、命令文档、gate 都不具备硬阻断能力。

所以：

- `gate` 更像“流程内检查器”
- `watch` 更像“流程外报警器”
- 真正的阻断要靠宿主权限、工具代理或工作区隔离

### 2. 目标不是 100% 防跑偏

这是不真实的承诺。

更现实的目标是：

- 把违规发现时间从 1 小时压缩到 5 分钟甚至 30 秒
- 把“模型已经知道没做完却继续推进”转化为可见、可拦截的控制流
- 把“前面做过的用户选择后面没人知道”转化为结构化上下文
- 把“看起来有功能”升级成“真正闭环”

### 3. 规范不是万能药，但仍然值得继续做

因为即便不能完全控制模型，仍然可以持续提升：

- 违规暴露速度
- 需求完成度下限
- 交付质量一致性
- 过程可审计性
- 多模型横向对比能力

## 四、Harness 五维度

## 4.1 Constraints

作用：告诉模型“什么不能做、什么必须先做、什么改了就算违规”。

典型问题：

- 用户一催，模型就跳过 `/spec:propose` 或 `/spec:apply`
- review 失败后，模型不补代码而是改低 `spec.md`
- AI 明知 task 没做完，还继续进入下一个 task

这一维度关心的不是“模型能不能理解需求”，而是：

**模型有没有被清楚地限定边界。**

当前已经落地或正在落地的能力：

- Stage Lock
- Spec Contract Freeze
- Task Self Assessment Gate
- 复杂需求 `test` 阶段必经

后续该维度要继续补的重点：

- 更明确的阶段升级/降级规则
- 更细的“允许修改 / 不允许修改”边界
- 更少依赖模型自觉的硬性检查

## 4.2 Feedback Loops

作用：尽快告诉我们“模型偏了、假了、没闭环、没验证”。

典型问题：

- 模型一口气改完源码，根本不给 gate 触发机会
- 跑了 gate，但 gate 证据可以伪造或过期后继续冒充有效
- 问题要到 review 或 archive 才暴露，返工太晚

这一维度关心的是：

**偏差能多快被发现，证据是否可信。**

当前已经落地或正在落地的能力：

- Gate Evidence / Sentinel
- Trust Level / Score
- `spec-copilot watch`
- review/test/archive 的证据链校验

后续该维度要继续补的重点：

- 更早期的报警
- 更贴近真实主流程的自动检查
- 把“未验证”与“验证失败”清楚区分

## 4.3 Tool Orchestration

作用：让模型不是“自己想怎么干就怎么干”，而是被引导走明确的工具入口和产物入口。

典型问题：

- 模型手写 `spec.md`、`tasks.md`、`log.md`
- 模型把框架命令当参考，而不是当唯一合法入口
- 宿主工具和规范之间没有握手机制

这一维度关心的是：

**流程是不是被编排成了可执行、可签发、可感知的工具链。**

当前已经规划但未完全成型的能力：

- `scaffold`
- 新 change 的签发痕迹
- 面向不同宿主的 adapter / command skill / wrapper

后续该维度要继续补的重点：

- CLI 入口统一
- 自定义命令 / skill 化
- 与 opencode、Codex、Claude、Cursor 等宿主的接合方式

## 4.4 Structured Context

作用：把执行过程中真正影响后续判断的信息留下来，而且能被后续阶段消费。

典型问题：

- 用户中途做了选择，但 reviewer 不知道
- AI 因环境限制降级，但 archive 看起来像“全部完成”
- 前面假设了某件事，后面没人验证它是否仍成立

这一维度关心的是：

**上下文是否被结构化保存，而不是散落在聊天记录和模型记忆里。**

当前已经落地或正在落地的能力：

- `log.md` Lifecycle Trace Ledger
- `Decision Ledger`
- `Risk / Evidence / Assumption` 区块
- `review.md` 独立审查结论

后续该维度要继续补的重点：

- 账本字段标准化
- 更多 gate 直接读取账本
- 归档后的知识沉淀与复用

## 4.5 Entropy Control

作用：降低复杂任务在执行过程中不断发散、铺开、偷工减料的概率。

典型问题：

- task 太大，模型同时改很多层，最后每层都只做了一半
- 任务按技术层拆分，导致“页面有了、接口有了、保存没落库”
- 模型越做越散，最后只能靠解释收尾

这一维度关心的是：

**如何把复杂性切成模型更容易稳定完成的闭环。**

当前已经规划但仍需加强的能力：

- Task Vertical Slice
- 更合理的 task 颗粒度
- 不可降级项
- 契约闭环检查

后续该维度要继续补的重点：

- 拆任务规则
- 主流程最小闭环优先
- 契约一致性和真实落库验证

## 五、用五维度重看当前版本演进

下面这张表保留版本事实，但不再把版本号当主叙事，而是说明每版主要补的是哪类 harness 能力。

| 版本 | 主题 | 主要维度 | 作用 |
|---|---|---|---|
| `v4.0.16` | Stage Lock | Constraints | 降低用户催促导致的越阶段执行 |
| `v4.0.17` | Gate Evidence Hardening | Feedback Loops | 让 gate 证据可追溯、不可手写伪造 |
| `v4.0.18` | Spec Contract Freeze | Constraints | apply 后冻结需求契约，防止改低 spec 过审 |
| `v4.0.19` | Watch | Feedback Loops | 抓完全不走 gate、直接改源码的行为 |
| `v4.0.20` | Task Self Assessment | Constraints + Structured Context | 把 AI 已自述的低分和降级转成 gate 输入 |
| `v4.0.21` | Lifecycle Trace Ledger | Structured Context | 让用户决策、假设、风险和验证限制贯穿后续阶段 |

一个更重要的结论是：

**截至 `v4.0.21`，我们已经在 Constraints、Feedback Loops、Structured Context 三个维度打下基础，但 Tool Orchestration 和 Entropy Control 还明显偏弱。**

这也解释了为什么：

- 规范越来越能“看见问题”
- 但还不够能“组织模型按更稳的方式工作”

## 六、三轮实验对应的问题映射

把真实实验映射到五维度后，问题会更聚焦。

| 现象 | 本质问题 | 对应维度 |
|---|---|---|
| 模型默不作声直接干完源码 | 没有进入规范工具链，缺少早期暴露机制 | Feedback Loops / Tool Orchestration |
| review 不通过后倾向改低 spec | apply 后合同边界不够硬 | Constraints |
| task 自评 80/90 还继续 | 自评未转化为控制流 | Constraints |
| 用户中途做了选择，后面 reviewer 不认 | 决策没有被结构化传递 | Structured Context |
| 列表/详情/保存看起来都写了，但契约断裂 | task 切法不对，检查点太晚 | Entropy Control / Feedback Loops |
| 不同模型遵守程度差异很大 | 宿主和工具入口缺少统一编排 | Tool Orchestration |

所以后面迭代不能只盯着“模型为什么不听话”。

更可做的提问是：

- 它没被什么约束住
- 它的偏差为什么没更早暴露
- 它为什么能绕开工具入口
- 它前面的决策为什么没传到后面
- 它为什么在复杂任务下发散了

## 七、下一阶段路线图

这里的路线不再只是“下个版本做什么”，而是“先补哪类 harness 能力”。

### P1. Entropy Control 补强

这是下一阶段最该优先补的。

原因很现实：现在我们已经能看到很多问题，但很多问题是在 task 被拆得太粗之后才爆出来的。

优先事项：

- Task Vertical Slice
- task 颗粒度上限
- 每个 task 强制填写用户可验证闭环
- 每个 task 标出不可降级项
- 禁止“前端一批、后端一批、测试一批”的粗粒度拆法

预期收益：

- 降低模型一次铺太开的概率
- 提高单 task 真正做完的概率
- 降低“看起来有、其实没闭环”的情况

### P2. Tool Orchestration 补强

这是第二优先级。

原因是：如果模型根本不把规范命令当唯一入口，很多约束和反馈都会晚到。

优先事项：

- `spec-copilot scaffold`
- 新 change 强制签发痕迹
- 面向 opencode 的自定义命令版本
- 后续再扩到 Codex / Claude / Cursor skill 化

预期收益：

- 让 change 目录不再由模型自由手写
- 增加“有没有真正走框架入口”的可判断性
- 为后续宿主适配打基础

### P3. Feedback Loops 深化

这个维度不是没做，而是还要继续往前推。

优先事项：

- 强化 `watch` 的违规时序输出
- 补主流程契约闭环检查
- 补保存落库、字段路径错位、DTO/Map 滥用等检查
- 把 Playwright / E2E 降级原因写得更可读、更可追责

预期收益：

- 更早暴露“功能像是做了，其实没做透”
- 减少 review 阶段才发现大问题
- 更好地区分“环境限制”与“实现偷懒”

### P4. Structured Context 扩展

这条线要持续做，但可以边做边落地，不必等大版本。

优先事项：

- 扩展 Lifecycle Ledger 模板
- 统一 `Dxxx` / 假设 / 风险 / 偏差引用方式
- 让更多 gate 读取账本而不是只看 `spec.md`
- 让 archive 输出更真实的遗留与取舍摘要

预期收益：

- 减少 reviewer 与前序阶段“各说各话”
- 提高复盘和规范能力评估的证据质量

### P5. Constraints 微调

这一维度已经有基础，接下来更适合做精修，而不是无止境叠硬规则。

优先事项：

- 细化什么情况允许 amend
- 细化复杂需求的 `test` 必经规则
- 避免 gate 因规则死板而误伤真实用户选择

预期收益：

- 保留边界强度的同时减少误判
- 避免后续阶段和前序人类选择冲突

## 八、建议的版本节奏

如果按工程节奏推进，我建议不要把所有事情硬塞进一个版本里。

更稳的做法是分两段。

### 第一段：补“模型为什么总发散”

建议主攻：

- Task Vertical Slice
- task 颗粒度规则
- 不可降级项
- 契约闭环基础检查

这段的核心目标不是再加一个 gate，而是：

**让模型更容易把任务真正做完。**

### 第二段：补“模型为什么总绕入口”

建议主攻：

- scaffold
- 宿主命令入口
- opencode 自定义命令
- watch 与签发入口的配合

这段的核心目标是：

**让模型更难无痕绕开框架。**

这样分批的好处是：

- 每一批的效果更容易验证
- 不会把所有改动混在一起导致无法判断谁真的有用
- 也更适合你现在让不同模型逐版对比验证

## 九、对这套路线的总评价

如果继续把它当“规范提示词”，它会越来越像在跟模型斗智斗勇，而且边界很快会碰到天花板。

但如果把它当成一套 harness engineering system，这条路线仍然值得继续，而且方向是清楚的：

- `Constraints` 决定模型边界是否明确
- `Feedback Loops` 决定违规能否尽早暴露
- `Tool Orchestration` 决定模型是否被拉进统一入口
- `Structured Context` 决定后续阶段能否读懂前面的真实决策
- `Entropy Control` 决定复杂需求会不会在执行中发散

从当前状态看，我对这套规范的判断是：

**它已经不只是“能不能让模型听话”的问题了，而是在逐步形成一套可评估、可比较、可迭代的 AI 开发控制系统。**

这也是它继续做下去的真正价值。

---

## 十、接下来怎么用这份路线图

后续每一版迭代，都建议至少回答下面四个问题：

1. 这次主要补的是五维度中的哪一维
2. 它解决的是哪类真实实验里暴露的问题
3. 它能把问题暴露得更早，还是让问题更难发生
4. 它对强模型、弱模型、不同宿主的效果边界分别是什么

这样我们后面复盘时，讨论的就不再只是“版本号升级了什么功能”，而是：

**这套 harness 在哪个维度上变强了，代价是什么，收益是否真实。**
