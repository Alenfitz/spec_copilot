请按 AGENTS.md 中定义的 /apply 流程执行：

**变更名**：$ARGUMENTS

## 前置检查（缺一不过）

1. 运行 `npx @alenfitz/spec-copilot gate <变更名> apply`（跨平台门禁检查）
   - v2.2.0 新增：gate 会检查 tasks.md 的前后端 task 交织度和前端 task 粒度
   - 连续 > 3 个后端 task 未穿插前端 → gate fail（必须调整 task 顺序）
   - 单个前端 task 涉及 > 4 个 .vue 文件 → gate fail（必须拆分 task）
2. Gate 通过后：`git checkout -b feature/<变更名>`（如已在分支则跳过）
3. 告知用户当前分支名

## 逐 task 执行规则（铁律：一个 task 一停）

> **🛑 这是最重要的规则：完成一个 task 后必须完全停止，等用户说"继续"才执行下一个 task。**
> **禁止连续执行多个 task。禁止在一次回复中完成两个或更多 task。**
> **即使用户说"全部执行"或"一口气做完"，仍必须逐 task 停顿。**

每个 task 的执行流程：
1. 编码实现
2. 验证（编译/构建/运行）
3. **展示验证证据**（见下方验证证据要求）
4. **填写 commit 自评分卡**（见下方"自评分卡铁律"，未填或分数过低 commit-msg hook 会拒绝）
5. 立即 `git commit`（commit message 必须含分卡）
6. 更新 tasks.md 该 task 状态为 ✅
6. **🛑 停止。输出以下提示后结束回复：**
   ```
   ✅ T<n> 完成（<简述>）
   验证：<编译/测试结果>
   功能验证：<curl 输出 / 页面行为描述>
   已实现文件：<实际新增/修改的文件列表>
   Commit: <hash> <message>
   
   → 下一步：T<n+1>: <描述>
   → 说"继续"执行下一个 task
   ```
7. **等用户回复后才开始下一个 task**

### 验证证据要求（铁律）

> **编译通过 ≠ 功能完成。** 每个 task 必须提供与 tasks.md 验收标准匹配的证据。

- **后端 task**：必须执行 tasks.md 中定义的验证命令（curl），展示实际返回的 JSON/状态码。如果 curl 返回异常，该 task 不得标记为 ✅
- **前端 task**：必须说明页面可访问路径、核心交互是否可操作（表单有绑定、按钮有 handler、提交有反馈）。如果按钮的 handler 是空的 TODO，该 task 不得标记为 ✅
- **文件清单对照**：完成时对比 tasks.md 计划的文件列表和实际修改的文件列表。遗漏的文件必须说明原因

### 反"太嗨"必填字段（每个 task 标 ✅ 前都要填，由 CLI 强制）

完成一个 task 后，在 tasks.md 对应 task 段落填写下列字段。**任何一项留空，gate review 阶段会阻断，必须重做**：

1. **实际验证结果**：粘贴**原始未加工的命令输出**，必须以 `$ ` / `>>> ` / `HTTP/` 开头。禁止用"通过"、"返回正常"等总结代替。
2. **实际文件清单**：列出实际修改的文件，与计划对比，标注遗漏。
3. **本 task 已实现/未实现的功能点编号**：分别列出。无未实现也必须写"无"，留空 = fail。
4. **本 task 已实现/未实现的业务规则编号**：分别列出。无则写"无"，留空 = fail。
5. **覆盖的 API / 页面**：列出 APIxx / PAGExx 编号，无则写"无"。
6. **契约一致性自查**（涉及 API 时必填）：前端请求字段 vs 后端接收字段 + 响应字段风格 + 一致性结论。
7. **已知缺陷或 TODO**：留空 = fail，无则写"无"。
8. **简化或降级处理**：留空 = fail，无则写"无"。
9. **失败场景自我攻击**：列出 3 种本实现可能失败的场景及各自处理状态。少于 3 条 = fail。

> 关于失败场景：不要写"用户输错参数会失败"这种通用废话。要写本 task **具体逻辑**可能出问题的地方（如：并发更新同一行的丢失更新、特定字段为 null 时的 NPE、分页参数边界）。

### 自评分卡铁律（v2.1.0 引入）

> 你能在事后给自己打 40-50 分，说明你**有评估能力**。把这个能力前置到 commit 前，强制 mode-switch。

每个 task 的 commit message 末尾**必须**附下列结构（commit-msg hook 自动校验）：

```
[<变更名>] T<n>: <简述>

<可选的正文描述>

## 自评分卡
- 业需匹配度：8/10（每扣 1 分必须列出具体扣分点）
- 代码可投产度：7/10
- 我未做但应该做的事：______（必填，无则写"无"）
- 如果用户现在评分，给：75/100（含理由）
```

**评分规则**：
- 分卡 4 项缺一不可，缺即 commit 被 hook 拒绝
- 总分 < 60 → commit 被拒绝（必须改进或显式声明降级并告知用户）
- 总分 60-69 → 警告但放行
- 总分 ≥ 70 → 通过
- "我未做但应该做的事" 留空 → 拒绝（即使真的全做了也必须显式写"无"）

**自评思路**：跳出"生成模式"问自己——
- 用户现在拿到这个代码能干什么？不能干什么？
- spec.md 里我刚做的部分，哪条对得上？哪条对不上？
- 我是否在偷懒（hardcode/骨架/stub handler/缺校验）？

### 禁用语言

spec.md / tasks.md / log.md **任何位置**禁止出现下列词汇（lint 命中即 fail）：

```
基本完成、大部分、核心已实现、完美、圆满、非常好、整体可用、
初步可用、差不多、应该、估计、可能、一气呵成、大功告成、基本可用
```

必须用具体数字或编号替代。例：
- ✗ "核心功能基本完成"
- ✓ "F01-F08 已实现（grep 命中），F09-F23 未实现"

### Scope 偏差处理

- 如果执行中发现某个计划文件无法实现或需要跳过，**立即告知用户并等待确认**，不得静默裁切
- 偏差发生时当场记录到 log.md `Spec-Code 偏差记录`（log.md 已在 /spec:propose 时从模板创建，直接编辑已有文件，不得重建）
- 禁止以"文件数太多"、"不属于当前 task 范围"为由裁减 spec 中已定义的功能

## 全部 task 完成后

1. 填写 tasks.md "变更摘要"
2. 输出完成报告：
   ```
   ━━━━━━━━━━━━━━━━━━━━━━━━━━━
   /spec:apply 全部完成 ✓
   总 Task：<N> 个
   总 Commit：<N> 个
   
   → 下一步：/spec:smoke <变更名>
   ━━━━━━━━━━━━━━━━━━━━━━━━━━━
   ```
3. **停止。等用户触发 /spec:smoke。**

核心原则：**AI 负责执行，用户负责推进节奏。** 任何阶段跳转都需要用户显式触发。
