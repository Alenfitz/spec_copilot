请按 lite 流程处理需求：

**需求描述**：$ARGUMENTS

## 适用范围

🟢 轻量需求：不改 API 契约 + 不改表结构 + 不改核心流程 + 不引入新依赖。

如不满足 → 建议改用 `/spec:propose`。

## Step 1 — 5 节迷你 Spec（直接在对话里写，不建文件）

```
## 1. 做什么
一句话描述

## 2. 为什么
（如果是修 bug：症状 + 根因）

## 3. 怎么改
- 文件 A：改什么
- 文件 B：改什么

## 4. 怎么验证
- curl xxx 应返回 yyy
- 页面 zzz 应有 www 行为

## 5. 风险
（影响哪些已有功能，无则写"无"）
```

## Step 2 — 等用户一句"开始"

不要在用户确认前编码。

## Step 3 — 直接实现 + 验证

1. 编码
2. 自测（运行验证命令，展示原始输出）
3. 用户确认 OK
4. `git add` + `git commit -m "<简述>"`

## 完成后

输出：
```
✅ 完成
- 改了：（实际文件列表）
- 验证：（命令输出摘要）
- Commit: <hash>
```

## 与 /spec:propose 的区别

| 维度 | /spec:lite | /spec:propose |
|------|-----------|--------------|
| spec 文件 | 不建（对话里写 5 节） | 必建 |
| tasks 拆分 | 不拆 | 必拆 |
| gate 检查 | 跳过 | 必跑 |
| 适用场景 | bug 修复、小功能、UI 调整 | 新功能、新接口、改表结构 |
| 节奏 | 一次性做完 | 逐 task 停顿 |

## 边界

如果实施过程中发现影响面比预期大（要改接口/表/核心流程），**立即停下**并提示用户：
> "这个需求实际触及了 X，建议改用 /spec:propose 走完整流程。"
